### Requirement: Output requests SHALL be registered from observations
The system MUST create one output entry for each valid observable point in each
observation whose domain is time-based or frequency-based. Evidence: VERIFIED.

#### Scenario: Valid observable point is registered
- **WHEN** a simulation has one observation with one observable point,
  a time-domain range, a case root of `case`, an output name of `probe`,
  a requested electric x component, and coordinates `(4, 4, 4)`
- **THEN** exactly one output entry exists with state `registered`, component
  `electric-x`, main coordinate `(4, 4, 4)`, and probe folder
  `case_probe_Ex_4_4_4`
- **AND** a time data file exists at
  `case_probe_Ex_4_4_4/case_probe_Ex_4_4_4_tm.dat`

### Requirement: Each probe SHALL own an output folder
The system MUST create a dedicated folder for every registered probe and MUST
place every file generated by that probe inside that folder. Evidence: VERIFIED.

#### Scenario: Probe folder and file basename are derived from probe identity
- **WHEN** a registered probe has identity path `case_probe_Ex_4_4_4`
- **THEN** the system creates a folder named `case_probe_Ex_4_4_4`
- **AND** the probe's generated files use `case_probe_Ex_4_4_4` as their
  basename inside that folder
- **AND** no probe-generated data file is written beside the folder

#### Scenario: Time-domain file is generated inside the probe folder
- **WHEN** a registered probe has identity path `case_probe_Ex_4_4_4` and
  generates time-domain scalar data
- **THEN** the time-domain file path is
  `case_probe_Ex_4_4_4/case_probe_Ex_4_4_4_tm.dat`

#### Scenario: Frequency-domain file is generated inside the probe folder
- **WHEN** a registered probe has identity path `case_probe_Ex_4_4_4` and
  generates frequency-domain scalar data
- **THEN** the frequency-domain file path is
  `case_probe_Ex_4_4_4/case_probe_Ex_4_4_4_fq.dat`

#### Scenario: Observation without a supported domain is skipped
- **WHEN** an observation has no time-domain configuration and no
  frequency-domain configuration
- **THEN** no output entry is created for that observation
- **AND** the observation-present flag remains false unless another valid
  output or transmission-line observation exists

#### Scenario: Wire-current observable is requested without active wires
- **WHEN** an observation requests wire current and the simulation state says
  no wire model is active
- **THEN** no wire-current output entry is created for that observable
- **AND** the output entry count excludes that observable

### Requirement: Output registration SHALL expose whether observations exist
The system MUST set the observation-present flag according to registered
outputs and active transmission-line observations. Evidence: VERIFIED.

#### Scenario: At least one output is registered
- **WHEN** output initialisation creates one or more output entries
- **THEN** the observation-present flag is true
- **AND** an output-request register is written

#### Scenario: No output is registered
- **WHEN** output initialisation creates zero output entries and no active
  transmission-line observation is present
- **THEN** the observation-present flag is false
- **AND** no output-request register is written

#### Scenario: Active transmission-line observation exists
- **WHEN** no ordinary output entry is created but at least one
  transmission-line probe is marked as present in the current layer
- **THEN** the observation-present flag is true

### Requirement: Output-request register SHALL list generated outputs
The system MUST write an output-request register whenever registered outputs
exist. Evidence: VERIFIED.

#### Scenario: Register is created for registered outputs
- **WHEN** output initialisation registers `N` outputs for a case root `case`
  and execution index `1`
- **THEN** a text register exists at `case_Outputrequests_1.txt`
- **AND** the register contains one line per generated file path or probe
  folder path, followed by a final line equal to `END!`

### Requirement: Output domains SHALL be normalised before registration
The system MUST normalise time and frequency domains before using them to
create outputs. Evidence: VERIFIED.

#### Scenario: Time step is smaller than the simulation step
- **WHEN** an observation requests time start `1.0`, time stop `2.0`,
  output step `0.05`, and the simulation step is `0.1`
- **THEN** the registered domain has time step `0.1`
- **AND** the time start remains `1.0` because it is not less than `0.1`

#### Scenario: Time start is before the first output interval
- **WHEN** an observation requests time start `0.05`, time stop `2.0`,
  output step `0.1`, and the simulation step is `0.1`
- **THEN** the registered domain has time start `0.0`
- **AND** the registered domain has time step `0.1`

#### Scenario: Requested time interval is shorter than the output step
- **WHEN** an observation requests time start `1.0`, time stop `1.05`,
  output step `0.1`, and the simulation step is `0.1`
- **THEN** the registered domain has time stop `1.1`

#### Scenario: Frequency domain is registered
- **WHEN** an observation requests initial frequency `0.0`, final frequency
  `100.0`, frequency step `20.0`, and simulation step `0.1`
- **THEN** the registered domain contains six frequency slots
- **AND** the generated frequency values are `0.0`, `16.666666...`,
  `33.333333...`, `50.0`, `66.666666...`, and `83.333333...`

### Requirement: Unsupported output requests SHALL stop registration
The system MUST reject an observable whose request type is not one of the
supported output request values. Evidence: VERIFIED.

#### Scenario: Unsupported request type is encountered
- **WHEN** an observable has a supported domain but a request type outside
  the recognised point, wire, block, volumetric, far-field, and map values
- **THEN** registration stops with the fatal message
  `OutputRequestType type not implemented yet on new observations`
- **AND** no later observable in the same registration pass is guaranteed to
  be registered

### Requirement: Time stepping SHALL dispatch only registered outputs
The system MUST update every registered output according to its output type at
each requested simulation time index. Evidence: VERIFIED.

#### Scenario: Registered outputs are updated
- **WHEN** the update trigger is called for time index `2` and the simulation
  time array stores `0.1` at index `2`
- **THEN** every registered time-sensitive output receives the time value `0.1`
- **AND** geometry-map outputs remain unchanged during the update trigger

#### Scenario: Unknown output type is updated
- **WHEN** a registered output has an unrecognised output type during update
- **THEN** the update trigger stops with the fatal message
  `Output update not implemented`

### Requirement: Flush SHALL persist pending output data
The system MUST flush registered outputs to files inside their probe folders
according to
their output type. Evidence: VERIFIED.

#### Scenario: Ordinary outputs are flushed
- **WHEN** the flush trigger is called while point, wire, block, movie, or
  frequency-slice outputs have pending data
- **THEN** each output writes its pending data inside its declared probe folder
- **AND** geometry-map outputs are not changed by the flush trigger

#### Scenario: Far-field flush is not requested
- **WHEN** the flush trigger is called with the far-field flush flag false
- **THEN** far-field outputs do not write far-field flush data

#### Scenario: Far-field flush is requested
- **WHEN** the flush trigger is called with the far-field flush flag true
- **THEN** far-field outputs write far-field flush data using the current
  simulation time
